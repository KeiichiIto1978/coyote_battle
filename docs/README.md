# ドキュメント管理方針

このディレクトリでは、Coyote Battleの現在の仕様と、長期的に参照する設計判断を管理します。

## 情報の役割

- GitHub Issue: 要望、議論、選択肢、詳細設計、テストケース、受け入れ条件、作業状況
- `proposal.md`: プロダクトの目的、ゲーム概要、初期要件
- `specifications/`: 機能や関心事ごとの現在の詳細仕様
- `decisions/`: 重要な設計判断と理由を記録するADR
- Pull Request: Issueで合意した内容の実装と、コード・文書をまとめたレビュー

## 現在の仕様書

- [品質ゲート](specifications/QualityGates.md): formatter、lint、pre-push、CI、Unity EditModeテストの運用
- [リリースCI](specifications/ReleaseCi.md): releaseブランチ、Unity Build Automation、Android APKの運用
- [参加者・ライフ・脱落](specifications/ParticipantRules.md): 固定5名、識別子、ライフ、脱落、失敗契約
- [宣言・ラウンド敗者判定](specifications/DeclarationRules.md): 数字宣言、コヨーテ宣言、履歴、敗者判定

## 基本方針

Issueごとの仕様書は作りません。Issue単位で文書を作ると、同じ機能の情報が複数ファイルへ分散し、現在の正しい仕様を探しにくくなるためです。

リファインメントでは、実装前にIssue上で仕様、詳細設計、テストケース、受け入れ条件を可能な範囲で決めます。仕様変更時は、その合意事項を対象機能の既存文書へ整理して転記します。適切な文書がない場合だけ、`specifications/` に機能や関心事を表す文書を追加します。

リポジトリ内の仕様書には、Issueで決まった内容に加え、実装中に判明・確定した制約、例外、技術的な補足、追加テストケースを反映します。議論の経緯を丸ごと複製するのではなく、実装後も参照すべき結論を現在形で記述します。

Issueで合意済みの内容をリポジトリ内ドキュメントへ反映する際、文書だけの事前承認は必要ありません。実装と文書を同じPRに含め、PRレビューで整合性を確認します。

## 推奨する仕様書の構成

```text
# 機能名

## 目的
## 用語
## 振る舞い
## 詳細設計
## 制約・例外
## テストケース
## 受け入れ条件
## 未決事項
```

不要な節は省略できます。Issue番号や変更履歴を文書本文へ毎回蓄積する必要はありません。履歴はGitとPRから追跡します。

## ADRを残す基準

アーキテクチャ、永続化方式、外部依存、複数機能へ影響する技術選択など、後から「なぜこの設計か」を確認する必要がある判断だけをADRとして残します。命名や局所的な実装方法など、容易に変更できる判断は対象外です。
