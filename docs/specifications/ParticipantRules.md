# 参加者・ライフ・脱落仕様

## 目的

Version 1のユーザーとNPCを操作方法に依存しない共通モデルとして扱い、ゲーム全体を通じてライフと参加資格を矛盾なく管理する。

Domain層は`MonoBehaviour`、シーン、端末APIへ依存しない。表示、入力、NPCの判断、ゲーム進行は上位層の責務とする。

## Version 1の参加者

参加者は次の固定5名とし、記載順を生成順とする。

| 識別子 | 種別 | 初期ライフ |
| --- | --- | ---: |
| `user` | ユーザー | 3 |
| `npc-1` | NPC | 3 |
| `npc-2` | NPC | 3 |
| `npc-3` | NPC | 3 |
| `npc-4` | NPC | 3 |

識別子はVersion 1内で同じ参加者を参照する安定した内部キーであり、空文字または空白だけの値を許可しない。表示名や永続化形式としては扱わない。

参加者の追加、削除、人数変更、初期ライフ変更を行う設定機能は提供しない。

## 参加者モデル

ユーザーとNPCは共通の`Participant`モデルで表現する。参加者は次の状態を持つ。

- 生成後に変わらない識別子
- `User`または`Npc`の種別
- 0以上3以下のライフ
- ライフ0から導出される脱落状態

識別子と種別は生成後に変更できない。ライフはDomain内の敗北適用によってのみ変更でき、外部から任意値を設定できない。

表示名、アイコン、外見、操作方法、NPC思考タイプ、手札、手番は参加者モデルへ含めない。

## ライフと脱落

有効なラウンド敗北を1回適用するたび、対象参加者のライフを1だけ減らす。

ライフ1の参加者へ敗北を適用すると、同じ操作内でライフ0となり脱落する。脱落状態は別の可変フラグとして保持せず、`Life == 0`から導出するため、ライフと脱落状態が矛盾する状態は存在しない。

脱落済み参加者へ敗北を再適用した場合は失敗を返し、ライフ0を維持する。ライフは負数にならない。

## 参加者管理

`ParticipantRoster`は固定5名を生成順で保持する。

- 全参加者一覧は脱落者を削除せず、常に固定5名を生成順で返す。
- 残存参加者一覧はライフ1以上の参加者だけを、全参加者一覧と同じ相対順序で返す。
- 両方の一覧は読み取り専用とし、呼び出し側から追加、削除、並べ替えを行えない。
- 識別子検索は既知のIDに対応する同一参加者を返す。

脱落者を全参加者一覧へ残すことで、ラウンド履歴と最終状態を参照できる。カード配布と宣言の対象には残存参加者一覧を使用する。

## 失敗契約

- null、空文字、空白だけの識別子は入力エラーとして引数例外で拒否する。
- 未定義の参加者種別は入力エラーとして拒否する。
- 形式上有効だが存在しない識別子の検索と敗北適用は`false`を返す。
- 脱落済み参加者への敗北適用は`false`を返す。
- 失敗時は対象者と他参加者のライフ、脱落状態、参加者一覧を変更しない。

## 他機能との境界

- カード配布結果は参加者識別子を配布先キーとして使用する。
- 残存参加者の抽出はDomain層、本一覧をカード配布・宣言へ渡す処理はゲーム進行を担うApplication層の責務とする。
- ユーザー脱落による敗北とNPC全滅による勝利はゲーム進行で判定する。
- ゲームを最初からやり直す場合は、既存参加者を任意状態へ戻さず、既定ファクトリから新しい参加者管理を生成する。
- 表示名はPresentation層またはApplication層、NPC思考タイプはNPC判断機能で対応付ける。

## Version 1の対象外

- 表示名、アイコン、外見の管理
- NPCの性格と意思決定
- カード、宣言、手番、ラウンド、ゲーム終了の管理
- 参加者状態のセーブとロード
- 参加者数と初期ライフの設定変更
- 既存参加者を任意のライフへ戻すリセットAPI
