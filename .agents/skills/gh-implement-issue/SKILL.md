# Issue実装とPR起票

## 開始条件

- `AGENTS.md`と対象Issueの本文・コメントを読む。
- IssueがReady判定を満たすか確認する。重大な未決事項があれば実装せずリファインメントへ戻す。
- 対象リポジトリ、Issue、baseブランチ、既存PR、remoteを確認する。
- fetch後のahead／behindと作業ツリーを確認する。無関係な変更があれば勝手にstash、reset、混入せず停止して確認するか、対象Issue用の安全なworktreeを使う。

## 実装手順

1. 同名ブランチと既存PRを確認し、`codex/issue-<番号>-<短い説明>`形式を基本に作業ブランチを用意する。
2. Issueの各受け入れ条件を、テスト名、手動確認、証跡のいずれかへ対応付ける。
3. Red、Green、Refactorの順で小さく実装する。Redでは期待した理由で失敗したことを確認する。既存実装ですでに通る場合は無理に失敗させず記録する。
4. ゲームロジックとUIを分離し、既存アーキテクチャと命名規則に従う。
5. Issueの合意事項をReady判定時に特定した仕様書へ整理転記する。既存文書がなければ機能単位で新設し、重要な長期設計判断だけをADRにする。
6. 実装中に判明した技術的事実と追加テストケースを仕様書へ反映する。振る舞いを変える制約や例外は推測で確定せず、Issueを再リファインする。
7. formatter、対象テスト、可能なら全テストを実行する。
8. 受け入れ条件を一つずつ検証し、未達がないことを確認する。
9. 差分を自己レビューし、問題を修正する。
10. 対象ファイルだけをstageし、status、baseとの差分、staged差分、機密・生成物の混入を確認してcommitする。hookを迂回しない。
11. remoteとheadを再確認して非forceでpushし、remoteのcommitと一致することを確認する。

## PR起票条件

次をすべて満たすまでPRを起票しない。

- 受け入れ条件を満たす
- 必要なテストが成功
- lint、コンパイル警告、既知の失敗を放置していない
- 仕様書と実装が一致
- 不要な差分や機密情報がない
- コミットが作成され、ブランチをpush済み

条件を満たしたら既存PRがないことを確認し、base、head、リポジトリを明示して`.github/pull_request_template.md`に従うReady PRを起票する。完了させるIssueは`Closes #<番号>`で関連付ける。作成後にURL、本文、base、head、Issue連携を確認する。PRをマージしない。

未達条件がある場合は原則PRを作らない。ユーザーが途中成果の共有を明示した場合だけ、未達条件と影響を本文に記載し、`Refs #<番号>`を使うDraft PRを許容する。push後にPR作成だけ失敗した場合はブランチを保持し、エラーと再開方法を報告する。

テスト失敗、競合、認証、push、PR作成の失敗を迂回しない。作業を保持し、状態、影響、再開条件を報告する。

## 報告

- PR URL、Issue番号、変更概要、テスト結果、仕様書更新、残課題を報告する。
- 実行できなかった検証は、理由と影響を明記する。
