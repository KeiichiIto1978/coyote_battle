# GitHub Issueリファインメント

## 原則

- Issueを要望、議論、詳細設計、テストケース、受け入れ条件の合意場所とする。
- Issue本文は最新の合意を読める状態に保ち、議論履歴はコメントに残す。
- 実装は行わない。コード調査は設計と見積もりの根拠を得るための読み取りに限定する。
- GitHub操作は接続済みGitHubツールを優先し、必要な場合だけ`gh` CLIを使う。更新失敗時は再実行で重複コメントを作らず、現在状態を再取得する。

## 手順

1. Issue本文、全コメント、本文やコメントから直接参照されたIssue／PR、関連仕様、コード、既存テストを読む。ページ送りがある場合は最後まで取得する。
2. 現状、期待結果、対象外、依存関係、リスク、未決事項を抽出する。
3. サブエージェントが利用可能なら、次を読み取り専用で独立に依頼する。
   - 仕様の曖昧さと境界値の洗い出し
   - テストケースと受け入れ条件の不足確認
   生のIssueと関連資料だけを渡し、結論を誘導しない。
4. 実装結果を左右する選択肢を、推奨案、根拠、トレードオフとともにIssue上で確認する。返答が必要な場合は確認コメントを投稿し、`Not Ready`として停止する。返答後は最新状態を再取得して再開する。
5. 合意後、Issue本文をIssueフォームと同じ順序・見出しで更新する。
   - 種別
   - 概要
   - 背景・目的
   - 対象範囲
   - 対象外
   - 詳細設計
   - テストケース
   - 受け入れ条件
   - 実装タスク
   - 依存関係
   - 制約・関連情報・未決事項
6. 実装タスクは依存順のチェックリストにし、各項目を検証可能な単位にする。
7. 大きな編集を行った場合は、決定事項と残課題をIssueコメントへ要約する。
8. Issue番号、URL、Ready判定、更新内容、決定事項、残課題、確認結果を報告する。

## Ready判定

次をすべて満たす場合だけ`Ready`と報告する。

- 目的と利用者価値が明確
- 対象範囲と対象外が明確
- 正常系、異常系、境界値のテストケースがある
- 受け入れ条件が検証可能
- 実装タスクと依存順が明確
- `Blocked by`、`Blocks`、`Related`が区別され、循環依存がない
- 重大な未決事項がない
- 更新が必要なリポジトリ内仕様書を特定済み

満たさない場合は、未決事項と次の確認相手を明記して`Not Ready`とする。
