# PR批判的自己レビュー

## 原則

- 承認する理由探しではなく、壊れる条件と見落としを探す。
- PR説明だけを信頼せず、Issue、仕様、差分、テスト結果を突き合わせる。
- 根拠のない懸念や好みだけの指摘は出さない。
- レビュー依頼だけの場合は、コード変更、コメント投稿、承認、マージを行わない。

## 手順

1. PR本文、対応Issueとコメント、関連仕様、全差分、CI結果を読む。
2. 変更箇所だけでなく、その入力元と利用先を追跡する。
3. 次の観点で確認する。
   - 受け入れ条件と仕様への適合
   - 正常系、異常系、境界値、状態遷移
   - 回帰、互換性、データや状態の破損
   - アーキテクチャ、命名、コメント、ファイル行数
   - テストの妥当性、未検証経路、偽陽性
   - セキュリティ、性能、端末差、Unityライフサイクル
   - 仕様書と実装の不一致
4. サブエージェントが利用可能なら、生のIssue、仕様、差分を渡し、読み取り専用かつ投稿・編集禁止で独立レビューを依頼する。主担当は指摘を再検証してから採用する。
5. 実行可能なテストや静的検査を行い、結果を証拠として使う。

## 出力

問題を重要度順に示す。

- `P0`: 即時対応が必要な致命的問題
- `P1`: マージ前に必須の重大問題
- `P2`: 通常はマージ前に直す問題
- `P3`: 改善候補

各指摘には、短い題名、影響、再現条件または根拠、ファイルと行、推奨対応を書く。問題がなければその旨を明示し、確認できなかった範囲と残存リスクを示す。

実装中の自己レビューとして呼ばれた場合は、確認された問題を修正して再検証する。既存PRのレビューとして呼ばれた場合は、ユーザーが修正も依頼したときだけ変更する。
