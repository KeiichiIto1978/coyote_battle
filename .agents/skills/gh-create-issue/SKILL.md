# GitHub Issue起票

## 原則

- `AGENTS.md`、`docs/README.md`、`.github/ISSUE_TEMPLATE/development.yml`に従う。
- Issueは議論の出発点であり、未確定事項を確定事項のように書かない。
- 既存Issueを検索し、重複する場合は新規起票せず候補を示す。
- 依頼を無条件に1件へ詰め込まず、独立して実装、レビュー、検証できる単位へ適宜分割する。
- GitHub操作は接続済みGitHubツールを優先し、必要な場合だけ`gh` CLIを使う。

## 手順

1. 依頼内容、`docs/proposal.md`、関連仕様、関連コードを確認する。
2. 依頼を次の基準で分割する。
   - 1つのIssueは、1つの目的と検証可能な成果を持つ。
   - 単独で実装、レビュー、テスト、リリース判断できる変更は分ける。
   - 前提作業、機能実装、後続改善に依存関係がある場合は分け、実施順を明記する。
   - 分割すると動作しない、意味のある成果にならない、同時変更が不可欠な場合はまとめる。
   - ファイル単位や作業手順だけで細分化せず、利用者または開発者にとって意味のある成果単位にする。
3. 既存のOpen／Closed Issueを検索し、分割候補ごとに重複と関連Issueを確認する。Openの重複候補は、ユーザー確認後に新規起票せずリファイン対象にする。Closedの候補は終了理由を確認し、再Open、新規起票、関連付けのいずれにするか確認する。
4. 各Issueについて次を整理する。
   - 種別と短いタイトル
   - 背景・解決したい問題
   - 対象範囲と対象外
   - 現時点で分かる詳細設計
   - 想定テストケース
   - 検証可能な受け入れ条件
   - 未決事項、制約、関連情報
5. 結果やIssue境界が大きく変わる不足情報だけを質問する。軽微な不足は仮定として明記する。
6. 種別に応じてタイトルを`[機能追加]`、`[不具合]`、`[改善]`、`[リファクタリング]`、`[テスト]`、`[依存関係・設定]`、`[ドキュメント]`で始める。
7. Issueフォームと同じ順序・見出しで本文を作る。未確定の節には`要リファインメント`と書く。
8. 分割後の依存関係を整理する。
   - 完了しないと着手または完了できない関係だけをハードブロックとする。
   - 各Issueに`Blocked by #<番号>`と`Blocks #<番号>`を相互記載する。GitHubの依存関係機能が利用できる場合は同じ関係を登録する。
   - 推奨順にすぎない関係は`Related #<番号>`とし、ブロック扱いにしない。
   - 循環依存がないことを確認し、あればIssue境界または設計を見直す。
   - 複数Issueを横断して進捗管理する価値がある場合だけ、親となる追跡Issueを作る。
9. ユーザーが起票を依頼していることを確認したうえでIssueを作成する。
10. 全Issueの番号、URL、分割理由、依存関係、推奨実施順、次にリファインメントすべき項目を報告する。途中で作成に失敗した場合は重複起票せず、作成済みIssueと未作成Issue、再開方法を報告する。

## 品質基準

- タイトルだけで変更対象と目的が分かる。
- 受け入れ条件は第三者が完了を判定できる。
- 各Issueは大きすぎず、単独でも意味のある完了状態を持つ。
- 分割後のIssue間に重複、要件の抜け、循環依存がない。
- 実装方法を必要以上に固定せず、確定済みの制約は落とさない。
- 機密情報、認証情報、個人情報をIssueへ記載しない。
