# GitHub Issue起票

## 原則

- `AGENTS.md`、`docs/README.md`、`.github/ISSUE_TEMPLATE/development.yml`に従う。
- Issueは議論の出発点であり、未確定事項を確定事項のように書かない。
- 既存Issueを検索し、重複する場合は新規起票せず候補を示す。
- GitHub操作は接続済みGitHubツールを優先し、必要な場合だけ`gh` CLIを使う。

## 手順

1. 依頼内容、`docs/proposal.md`、関連仕様、関連コードを確認する。
2. 既存のOpen／Closed Issueを検索し、重複と関連Issueを確認する。Openの重複候補は、ユーザー確認後に新規起票せずリファイン対象にする。Closedの候補は終了理由を確認し、再Open、新規起票、関連付けのいずれにするか確認する。
3. 次を整理する。
   - 種別と短いタイトル
   - 背景・解決したい問題
   - 対象範囲と対象外
   - 現時点で分かる詳細設計
   - 想定テストケース
   - 検証可能な受け入れ条件
   - 未決事項、制約、関連情報
4. 結果が大きく変わる不足情報だけを質問する。軽微な不足は仮定として明記する。
5. 種別に応じてタイトルを`[機能追加]`、`[不具合]`、`[改善]`、`[リファクタリング]`、`[テスト]`、`[依存関係・設定]`、`[ドキュメント]`で始める。
6. Issueフォームと同じ順序・見出しで本文を作る。未確定の節には`要リファインメント`と書く。
7. ユーザーが起票を依頼していることを確認したうえでIssueを作成する。
8. Issue番号、URL、要約、次にリファインメントすべき項目を報告する。作成に失敗した場合は重複起票せず、状態と再開方法を報告する。

## 品質基準

- タイトルだけで変更対象と目的が分かる。
- 受け入れ条件は第三者が完了を判定できる。
- 実装方法を必要以上に固定せず、確定済みの制約は落とさない。
- 機密情報、認証情報、個人情報をIssueへ記載しない。
